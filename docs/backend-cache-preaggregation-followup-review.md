# 后端缓存与预聚合后续审查

日期：2026-10-14。依据 0026、0027 实施后的当前工作区代码。本次仅审查并记录候选，不修改运行逻辑、不部署；以下优先级基于调用路径和数据增长方式，尚未逐项做生产压测。

## 已覆盖的部分

- `traffic_records`、`node_network_samples` → `traffic_minute_totals`；用户历史累计 → `user_node_usage`。
- `online_samples` → 全局/单节点 `online_cycle_metrics`；`proxy_probe_samples` 的尝试/成功数 → `probe_minute_totals`。精确延迟分位数仍读原始样本。
- 配置引用 → `credential_reference_edges`，删除/归档等校验同步处理待更新项。
- 多数管理 GET 已进入 Redis 响应缓存：概览 3 秒、历史 60 秒、任务/批次 1 秒、其他可缓存 GET 5 秒。目录快照、脱敏预览、订阅生成结果也已使用 Redis。
- 节点/用户/授权组/DNS/发布批次已有批量读取；SSE 已共享读取；安装包已有磁盘缓存。

因此剩余主要是缓存依赖划分、已有聚合的二级汇总，以及冷查询/大响应路径，不能把已经缓存的接口再次列作“未缓存”。

## 不增加普通缓存的部分

管理员放行、`/hy2/auth`、订阅资格、写入预览确认、修订冲突、凭据删除校验、任务领取/租约以及外部 DNS 写入确认继续以当前状态为准。`/readyz` 和主机监控的数据库探测不缓存“数据库正常”；主机资源已有两秒内存快照。SSE 继续使用持久回放和共享读取，不套 TTL 响应缓存。

## 实施顺序建议

1. 先修正质量趋势边缘 SQL 与历史读取中的不必要聚合/写锁。
2. 拆分缓存依赖版本，并补齐按路由的命中、回源耗时、Redis 错误/容量、聚合队列与写锁等待指标。现有 `/cache` 只有分类汇总，无法直接定位每条路由。
3. 根据冷查询与数据规模优先选择流量小时汇总、在线分钟汇总，再评估任务计数/重试链。
4. 大资源/授权组先处理传输体积和按需加载；延迟分布近似及审计分类统计待明确需求。

验收应同时比较缓存未命中、Redis 故障和新数据库连接下的耗时，以及与原始查询的精确对账，防止只有暖缓存快、首次请求仍退化。
