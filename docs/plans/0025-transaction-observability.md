# 事务冲突日志与生产归因

日期：2026-11-06。目标：先补齐日志并部署，再用生产证据决定优化或修复范围。按 10 万用户、1 万节点约束设计，不改变业务 SQL、事务隔离级别、重试预算、租约或收尾协议。

- 每次事务调用使用唯一 ID，自动记录闭包所属操作、隔离级别、阶段和执行身份。捕获 SQLx 查询事件，仅在失败时输出脱敏 SQL、指纹、SQLSTATE 和 PostgreSQL 内部函数位置，不记录绑定值、错误 detail 或秘密。
- 中间冲突在事务边界记录为重试事件；重试成功和最终耗尽分别记录。错误转换保留原有 HTTP 分类，在边界内部不再把可重试中间错误重复记为 ERROR。
- 每操作每分钟输出累计调用、尝试、冲突、成功、失败、耗尽、取消、耗时和延迟桶，提供分母；普通成功事务不逐条输出 INFO。观测不增加数据库往返。
- 验证真实 PostgreSQL 冲突、耗尽、业务错误、取消和 SQL 脱敏；检查任务局部上下文并发隔离以及原执行收尾回归。
- 本地构建 linux/amd64 镜像后传输，只替换 API 镜像；schema、生产环境配置与其他服务保持。保存生产配置、数据库备份、健康及认证/订阅验证结果。
- 上线至少观察 30 分钟，按操作、阶段、SQL 指纹与最终结果分析，核对业务状态、性能代价及采样例外。无法归因的部分明确保留，不把本地模型直接作为生产结论。依据实际结果决定是否需要后续修复。

## 已实施

统一事务边界记录 transaction_id（UUID）、闭包操作名、隔离级别、attempt/max_attempts、SQLSTATE、失败阶段、语句指纹/脱敏语句、语句/调用耗时、PostgreSQL 内部函数及工作 owner/generation/epoch。sampling_cycle span 补充队列种类。阶段区分 begin、guard、operation、finalization_validate、commit、rollback。内部成功回滚保留原失败语句；回滚失败保留清理失败现场。

SQLx 查询层只在任务局部的事务上下文中保留最后一条查询，不输出普通成功查询 DEBUG。脱敏去掉字符串、数字、注释和引用标识符；对普通字符串中含义不明确的反斜杠保守隐藏剩余 SQL。最多输出约 2 KiB，服务器上下文只保留函数标识符，不记录数据库 detail 或绑定值。没有为 backend PID 增加 SQL 往返；事务 UUID 和执行身份用于应用侧关联，不能声称恢复了服务器完整 SSI 图。

可重试的边界内错误转换不再提前输出 ERROR；retry 为 WARN，succeeded_after_retry 为 INFO，retry_exhausted 为 ERROR。原有错误分类、最多六次尝试、退避算法和收尾协议保持。非冲突业务错误仍按原分类返回；每操作每分钟输出累计计数和各延迟区间的累计样本数（10/50/100/250/500/1000/5000 ms 边界），普通成功调用不逐条记 INFO。摘要中的 failed 包含业务拒绝，不能直接当作数据库故障；取消不等同于确认回滚。

## 本地验证

8 项真实 PostgreSQL / 脱敏专项通过，覆盖重试成功及原 SQL 保留、六次耗尽、延迟约束提交失败、并发上下文隔离、业务拒绝与取消计数、重试后业务拒绝的可见终态、内部回滚保护和 SQL 脱敏。fmt、差异检查与沿用基线三项排除的 Clippy 通过。

最终冻结输入的 8 项专项通过；全量 1068 passed、1 failed、16 ignored，另行隔离执行的大规模删除 1 passed（原 30 秒 worker 时限保持）。没有宣称全量全绿。唯一失败为 `credentials::rotations::users::tests::concurrent_schedulers_stage_one_signature_without_releasing_or_publishing_it` 的第 646 行，期待立即签发 1 条而观察到 0 条；已提交基线与日志版本交替并发各 20 次，均 18 passed / 2 次相同断言失败。该现象在基线存在，本轮保留为已知间歇例外，不修改测试或扩展到签发业务修复。

一次较早运行被主机低电量休眠中断（北京时间 04:22:48～05:30:42），不计验收；恢复外接电源后在新数据库重跑。最终构建及验证输入未变化；结果和二进制摘要保存在本地 `target/transaction-observability/`。实际后台循环的 INFO 日志与分钟摘要烟测已在隔离数据库通过：94.30 秒，32 类摘要操作、9 次冲突尝试、8 个冲突调用全部成功闭环，结构化 SQL 指纹非空。该夹具不是生产 SSH、HTTP 或容量验收。

## 判断及后续范围

当前未观察到需要紧急处理的事务耗尽或业务失败，但不能把现象归为纯日志问题：后台维护确有持续重试和额外延迟，需要针对性优化。优先审查凭据清理、jobs 维护的工作元数据依赖、谓词读集和重复数据库往返，并减少无工作时的高频轮询；保持业务写入、租约释放、工作终态同事务原子提交。任何隔离调整都需逐路径证明业务不变量，不能直接全局降低隔离级别或扩大重试预算。

启动采样缺口作为重启接管问题单列继续定位，当前证据不能证明由 40001 引起。本轮仅部署观测增强，没有实施上述业务优化，也没有宣称完成 10 万用户 / 1 万节点容量验收。私密发布与归因材料保存在 `production/releases/20261106-transaction-observability-r1/`。
