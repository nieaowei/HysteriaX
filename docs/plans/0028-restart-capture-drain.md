# 重启时排空在途流量采集

日期：2026-11-07。状态：已部署并通过生产受控重启排空验收；稳定 25 分钟 450/450 完成，无新增清零不确定缺口，启动超窗和历史缺口仍保留。

## 问题与边界

0027 的生产切换发现两条旧进程批次已登记清零请求，但未持久化响应，随后过期/丢弃并保留 `traffic_clear_uncertain` 缺口。不能确认远程清零是否执行，也不能确认计量无损。代码中，SIGTERM 只通知 HTTP 排空；HTTP 返回后 main 直接 abort 所有后台 worker，连同 JoinSet 中正在接收或保存清零响应的任务一起取消。

本次修复正常 SIGTERM/退出路径，不修改清零单次发送、租约身份、采样准入截止、未知操作屏障或已捕获数据的恢复规则。历史缺口没有可重建的原始响应，不修改或补猜计量；SIGKILL、崩溃、网络响应丢失、数据库不可用及排空超时仍可能产生不确定结果。停机期间未执行的采样仍可能如实过期，不能承诺消除全部启动期失败。

按 10 万用户、1 万节点假设，排空仅等待当前受并发上限约束的本进程工作，不扫描全部节点，不接管其他实例租约，不使用全局采样锁或逐节点内存状态。

## 实施

1. 三类采样收到停机通知后停止创建周期和领取新工作，不取消已经发起的领取事务；领取完成后的工作仍进入受跟踪任务集合。原有任务集合等待至采集、捕获、计量页及工作确认返回，不因 HTTP 已结束而被直接取消。停机通知优先，其次回收已经结束的子任务，最后处理 tick，避免慢数据库令 timer 持续就绪、饿死 JoinSet 回收。
2. 流量在开始采集和清零准入前检查停机状态。准入前的同步检查是本地边界；已通过边界的在途流程继续完成单次清零和响应持久化。尚未准入者以 `shutdown_deferred` 原子让出工作及租约，保留原截止时间，不记作真实采集失败，也不伪造完成。
3. 让出事务保留身份校验、原子确认和释放屏障，并拒绝让出已经登记清零、尚未捕获的批次。这类批次必须走原有捕获或不确定结果处理，不能靠让出绕过。
4. HTTP 正常排空最多 8 秒。main 在 HTTP 结束或失败后确保通知停机，停止其他 worker，继续保留实例心跳、采样自身续租和事件发布，等待三个采样 worker，统一排空预算最多 120 秒。超时记录 ERROR、取消未完成 worker 并以错误退出，保留数据库中的恢复依据；worker 整体 panic 也不能作为排空成功。
5. 流量维护和代理保留清理循环响应停机，在当前有界操作返回后结束，使所属采样 worker 能完成 join。
6. Compose API `stop_grace_period` 设置为 150 秒，为 HTTP、采样排空和进程退出留出余量。备份/恢复三条停机路径从 60 秒改为 150 秒，避免外部先强杀；同步安装升级与备份文档。

无 schema、管理 API 或数据结构迁移。新错误码仅标记原工作安全让出，不改变计费记录。共享确认事务的结构化观测名由 `background::finish` 变为 `background::finish_or_defer`，后续对照计数需按新名称匹配。监听端口绑定移至 worker 启动前，避免绑定失败时已有远程采集被运行时退出打断。

## 验证

新增确定性回归覆盖：停机后不创建/领取采样；已登记但未捕获的请求禁止普通让出；排空超时和 worker panic 报错；真实 SSH 中清零响应被阻塞时停机必须继续等待，原 slot 过期后仍持久化响应、完成计量并释放租约，不重复收费；在清零准入前停机则不发送请求，原子让出后下一实例接管并只清零一次。

另增加显式忽略的真实服务器子进程用例，需要从同一源码构建的 `HYSTERIAX_TEST_SERVER_BIN` 和保留日志路径 `HYSTERIAX_TEST_SERVER_LOG`。它启动完整服务，等真实 SSH 收到清零请求，发送真实 SIGTERM，确认 HTTP 已停止而进程仍等待响应；放行后检查正常退出、17 字节计量、单次清零、零不确定缺口及租约释放。不能把未执行的忽略用例算作通过。

最终运行结果、冻结源码/二进制摘要及原始日志保存于本地受限目录 `target/restart-drain/`，结果见下文。

## 回归中发现的异步断言时序

首轮完整回归在第一个 32 项批次中出现 1 项失败、31 项通过：未改动的 `authenticated_reads_remain_available_while_writer_lock_is_held` 立即检查 `last_used_at`，而令牌使用时间戳由独立异步任务提交。候选单独运行 3 次、修复前冻结二进制同一 32 项批次运行 3 次均通过，未复现基线失败；不据此宣称已证明该失败由某版本造成。

代码审查发现，原用例先释放 writer 锁，再立即检查异步提交，既有调度竞争，也不能直接证明更新在持锁时完成。仅修正该测试：保留原请求成功/拒绝和最终更新时间断言，在 writer 锁仍持有时最多等待 2 秒，确认使用时间戳提交后才释放锁。没有修改令牌产品逻辑、元数据超时或断言目标。原失败批次及摘要保留在 `initial-regression-attempt/`，不计入最终套件通过数；最终冻结源码从头运行完整套件。

## 部署验收

本地实施阶段没有自动部署；用户随后明确授权部署，结果见下文。首次从旧镜像切换时，旧进程仍采用旧的强制取消行为；增大容器停机时间不能赋予旧二进制排空能力，需单独核对切换前在途清零记录，保留无法确认的缺口。新容器需要实际应用当前 Compose 停机配置；普通 `docker compose stop api` 使用配置等待，直接 Docker 停机显式使用 `--time 150`。

生产验收应对已运行本修复的进程执行受控停机/重启，分别记录停机前清零准入、在途数量、请求与响应落库、租约释放、排空完成/超时、接管后的批次计量和新增缺口。对比正常切换与稳定期，不能以 HTTP 就绪或稳定期采样成功替代交接验收，也不能将本地结果称作历史缺口已恢复。
