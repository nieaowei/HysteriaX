# 0033 Redis 实时节点额度排行

## 目标

节点额度排行最多展示 10 项。正常读取通过 Redis 获取排名，不再额外扫描、计算并排序全部套餐；PostgreSQL 继续作为计费数据源。

## 实施

1. 增加 `quota_rank` 模块，复用现有 Redis 连接、命名空间、150 ms 超时和两秒熔断。排行按数据库和 schema 隔离，使用有序集合及成员目录、重置时间索引、完整性版本标记。相关键空闲 600 秒过期。
2. 排序维持使用比例降序、数据库 `lower(name)` / 原名 / ID 升序。所有成员使用相同 score，通过固定长度的 64 位整数、128 位小数比例补码进行字典序排序，避免 double 精度丢失改变相邻大整数比例的顺序。Redis 原子脚本负责更新和读取前 10 项。
3. 迁移 0028 只在已有 `cache_domain_versions` 中增加一个版本行，并添加变更通知触发器；不增加表、计费字段或数据库比例计算。用量、额度、重置时间、节点名称、添加/删除和 TRUNCATE 在提交后发布通知；回滚不发布。仅采样时间、节点心跳等无关变化不推进排行版本。
4. 后台监听提交通知，按节点主键读取并增量同步。读取前比对数据库快照的排行版本；通知落后、批量变更产生版本缺口、Redis 数据丢失或键被独立淘汰时，使用一致性快照重建，防止返回缺项或旧排名。后台每秒通过主键检查版本并执行到期归零，正常检查不扫描套餐表。
5. 重置时间单独保存在 Redis 的时间有序集合中，读取前原子处理所有已到期节点；无需等待下一次网络采集，也不会改写数据库计费数据。概览响应缓存增加秒级时间边界，避免跨重置时间继续复用旧名次；原有源数据版本失效机制保留。
6. Redis 不可用时回源，恢复后自动重建。未配置 Redis 时保留原数据库排序。全量候选扫描仅用于未配置/故障回源、冷启动、缺失/落后版本恢复；并未宣称整个概览接口没有其他全局统计和节点摘要读取。
7. 新增无损回退脚本 `scripts/rollback-redis-quota-rank.sql`，停服务后先将 0028 回退到 0027，再使用以前的回退脚本。同步原有迁移回退集成测试。

## 数据与时效

- Redis 排行包含比例排序键、节点 ID、名称排序元数据及重置时间；不存储凭据、令牌、节点配置或原始流量记录。响应与其他业务缓存正文继续使用既有认证加密。排序元数据需要参与 Redis 排序，因此不属于加密正文。
- 实时指数据库中的用量/额度变更提交后同步排名。用量本身仍由原有采集周期提供，客户端仍按既有刷新周期获取页面，不新增推送。
- 增量通知只携带 schema、节点 ID 和版本，避免大量业务内容进入 PostgreSQL 通知队列。版本更新属于轻量数据库写入；Redis 方案不意味着数据库完全没有额外开销。
- 发生并发提交或通知缺口时优先通过重建保证正确性，可能产生一次额外扫描；不是只依赖定时全量重建。

## 验证

- 新增真实 Redis/PostgreSQL 集成测试，覆盖前 10、比例精度、主键增量同步、修改额度、取消额度、改名、删除、周期到点、事务回滚、独立键淘汰、实例替换、缺失通知、空集合、TRUNCATE、后台监听和 Redis 不可用。
- 持有 `node_packages` 的排他表锁，并给读取连接设置 200 ms 超时后，Redis 热排行读取仍成功，验证正常读取不访问套餐表。
- 完整后端测试 205 项通过（配置真实 PostgreSQL 和 Redis，未跳过新增集成用例）；严格 Clippy `--all-targets -- -D warnings`、格式与补丁空白检查通过。
- Swift API 生成一致性检查通过。
