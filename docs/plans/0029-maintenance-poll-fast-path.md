# 后台维护空轮询与租约往返修复

日期：2026-11-07。状态：已实施，定向功能及性能验证完成，尚未部署。完整非忽略回归 1103 项通过、1 项旧实现与候选均超时，整套检查尚未全绿。

## 依据与范围

生产只读定位记录在 `production/investigations/20261107-performance-location/REPORT.md`。三分钟维护领取调用 3432 次，对齐持久化代数变化约 603 次实际领取，空领取约 82%；领取和 ensure 平均耗时分别约 453/334 ms。租约锁关联样本中，76 组校验/续租等待有 73 组的持锁方处于事务内 ClientRead。远程简单命令对照确认顺序往返具有明显固定成本。

同节点三类采样共享一分钟窗口；一次稳定期代理任务到第 54.46 秒才开始，随后在远程采集前超窗。06:10 全局尖峰的最初触发因素未确定，且与运维读取重叠，不能把这一尖峰全部归因于上述路径。

本批减少已证明的空事务与多资源串行往返，不改变采样周期、节点互斥、超窗准入、租约有效期、事务隔离、重试预算或连接池上限。按 10 万用户、1 万节点设计：候选仍有界，提示无跨事务授权效力，不增加逐节点轮询或永久缓存。无 schema 变化，无需一次性数据迁移。

## 实施方案

1. ensure/ensure_many 对已存在且尚未到期的工作，先做非锁定单语句预检查；不需要变更时直接返回。有变更提示时，事务内用 SKIP LOCKED 和条件写入重新判断，不能重置活跃 owner、覆盖 payload 或提前入队。来自已有受监督执行作用域的调用保留事务入口校验。
2. claim/claim_id 先做不授予所有权的有界资格预检查；无候选时不开完整事务。有候选时仍在事务内重新选择、锁定和校验全部资源及未决操作屏障。将数据库时间合入候选语句，去掉单独时钟往返。不缓存空结果，也不延长既有一秒补查间隔。
3. 多资源领取复用既有有序 acquire_all；失败时仍回滚完整候选 savepoint 后继续下一候选。Work::guard_on 使用既有有序 guard_all，并在其后的新语句中检查工作身份；保留 READ COMMITTED 下锁后重新观察屏障的语义，不把不同快照要求强行合并。
4. 增加按维护 kind 汇总的预检查空返回、事务调用、实际领取、失败和取消计数，以便部署后直接计算空领取比例。仅输出有界维度的累计摘要，不记录业务 payload。

预检查和随后的第一次事务复用同一条池连接；事务冲突后仍由原边界在新事务中重试。`maintenance poll summary` 的 duration_us 覆盖连接获取、预检查及后续事务；旧 database transaction summary 只统计进入事务边界后的部分，不能直接将新旧事务均值当作整个领取调用的等口径比较。

领取结果分别累计 `empty`（最终返回 None）和 `claimed`（成功领取）。部署后可按同窗口差分计算 `Δempty / (Δempty + Δclaimed)`，排除失败、取消和边界在途；`preflight_empty` 单列其中绕过事务的部分，避免把事务成功误算成领取成功。

本批缩减空轮询的事务成本，并未实现依赖通知的长休眠调度。跨实例提前入队仍由原轮询间隔发现，没有仅依赖进程内提示或通知丢失造成的长期漏处理。

## 验证方案

- 冻结含相同基准入口的旧实现与候选测试二进制，使用同一隔离 PostgreSQL、相同固定输入和 25 ms 响应方向延迟，比较空轮询及 1/3/9 资源的领取/收尾。记录时长和 SQL 数量；预检查增加的非空成本也要报告。
- 真实数据库回归覆盖预检查后来源变化、两个实例同时领取、部分资源失败回滚、繁忙资源不遮挡后续候选、过期/旧 owner/generation/epoch、未决远程屏障与确认原子性。
- 使用 SQL 事件验证空路径只有预检查、没有 COMMIT，结合代码中在事务入口前直接返回的分支确认显式事务被跳过；验证校验合并没有随资源数量线性增加 SQL。运行受影响的后台、凭据、租约及采样回归与格式、静态检查。
- 本地验证不能代替生产性能或 10 万用户/1 万节点容量验收。部署后需另按相同窗口观察轮询命中率、连接获取、锁等待和采样质量；本轮修复指令不等同于本轮已经部署。

## 实施及验证结果

已完成预检查、同连接事务衔接、有序批量领取/校验和按 kind 汇总的结果计数。没有数据库迁移、配置变更或生产部署。

基准的 statements / begins 是 SQLx 查询日志事件计数，不是 PostgreSQL 协议的完整清单；SQLx 的事务起始路径不一定产生查询事件，因此 begins=0 不能单独证明未发送 BEGIN。性能判断采用端到端耗时、日志中实际观察到的查询事件、独立时钟查询数及显式事务入口分支，不把日志计数当作数据库隐式事务总数。

扩大回归暴露既有 `successful_internal_rollback_preserves_the_validation_failure_statement` 日志关联测试的作用域问题：冻结旧实现与候选各连续三次单独执行均未捕获原始 DO 语句。本轮仅修正该当前线程测试的 subscriber 生命周期，使其覆盖流析构；原阶段、SQL 和 SQLSTATE 断言保留，生产诊断逻辑未修改。单项复核通过后重新冻结候选，重新执行完整分批回归。证据为 `target/maintenance-poll-fix/trace-baseline-audit.json` 和 `trace-fixture-fixed.log`。

### 功能与静态检查

最终冻结候选的全部 1104 个非忽略服务端用例均已执行：1103 通过、1 失败。每个原生进程最多 32 项、4 个测试线程，8 个大规模用例分别单独执行；使用隔离 PostgreSQL 18.6，后续按批创建独立临时数据库。这是分批覆盖，不是一次完整套件进程通过。

通过的新增用例覆盖：空路径只有两条预检查且不提交显式事务、下一轮能发现外部提前入队、预检查后另一实例抢先领取、due 状态变更、过期租约关联的未知远程操作屏障、批量 guard 对旧代数的拒绝、继承失效执行作用域时不能绕过原事务入口、同连接衔接后冲突重试使用新事务并原子回滚。

保留失败项 `jobs::node_cleanup_tests::large_record_removal_is_queued_idempotent_and_completes_without_ssh`：其 worker 原有 30 秒完成时限没有放宽。原隔离实例与新建同规格实例中，旧实现和候选均出现相同超时；各完整用例约 40 秒包含准备时间，不能把 40 秒直接当作 worker 耗时。当前没有证据将这一失败归因于本轮，但该门槛确实未通过，不能宣称大规模记录清理或整体性能已经验收。证据为 `complete-39.log`、`large-baseline-audit.json` 和 `large-fresh-audit.json`。

fmt、diff 检查和 Clippy 通过；Clippy 沿用既有 large_enum_variant、too_many_arguments、await_holding_lock 三项排除。最终 crate 输入清单与交付工作区逐文件一致。未运行未改动的 macOS 或模板验证器独立测试。

### 受控性能对照

基线为当前已部署的业务实现 c586d0f（仓库基线 8f6b94f），另加入与候选一致的测量入口。使用同一隔离 PostgreSQL 18.6、固定逻辑数据、响应方向 25 ms 延迟；正序和逆序各测每场景 10 次，表中为合计 20 次的平均耗时。空闲场景是一轮 ensure + claim，非空场景为一次领取、受监督校验及收尾；资源数包含工作租约。

| 场景 | 基线均值 | 候选均值 | 均值下降 |
| --- | ---: | ---: | ---: |
| 空轮询 | 270.65 ms | 131.59 ms | 51.4% |
| 1 个资源 | 1099.54 ms | 1080.84 ms | 1.7% |
| 3 个资源 | 1441.16 ms | 1041.00 ms | 27.8% |
| 9 个资源 | 2816.02 ms | 1230.37 ms | 56.3% |

单资源正序略降、逆序略升，按基本持平解释，不宣称稳定改善。空轮询及多资源两种顺序均改善。每 10 次空闲轮询的 SQLx 查询事件从 70 降至 40；每 10 次领取的独立时钟查询从 10 降至 0。事件计数不是全部协议往返或数据库隐式事务数，且非空计数含并发续租，不按日志数量推算生产吞吐。

两版本测量源文件一致，前后二进制摘要均核实；原始结果保存在 `target/maintenance-poll-fix/compare-25ms-forward/`、`compare-25ms-reverse/`，汇总为 `performance-summary.json`，完整功能覆盖为 `regression-complete.json`。受控微基准不代表生产或 10 万用户/1 万节点容量验收，亦未定位或修复 06:10 全局尖峰的最初触发因素。

本轮本地 PostgreSQL、临时 worktree 和防休眠进程仅属于本次验证，清理记录另存于同目录。生产采样质量、连接获取和锁等待需部署后按同口径重新观察。
