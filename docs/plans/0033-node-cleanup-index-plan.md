# 0033 节点清理索引与断点恢复

## 线上证据

0032 部署后，实际业务节点的记录删除在累计清理 162,688 条记录后失败。
PostgreSQL 日志定位到选取下一批 `traffic_records` 的 SELECT，而不是 DELETE。
`ORDER BY sampled_at DESC,id DESC LIMIT 32` 的计划使用全表时间索引、过滤节点，
再做增量排序；扫描大量较新节点的数据，15 秒仍未完成。减小 LIMIT 不能解决启动扫描成本。

补充完整复合索引后，旧统计下优化器仍可能选择上述计划。事务内关闭增量排序后，
改用 `traffic_records_node_cleanup_idx` 且 `Index Cond` 限定节点；线上冷读 512 条约 997 毫秒。

## 实施

1. 迁移 0040 为原始历史表、用户节点汇总增加完整匹配节点、时间、记录 ID 排序的索引。
   现有大表在部署前逐表 `CREATE INDEX CONCURRENTLY`，验证有效后再启动迁移。
2. 清理事务使用定制计划并关闭增量排序，避免选择全局时间索引后过滤旧节点。
   保留每条 SQL 2 秒限制和缩小批次策略，限制全局写锁占用时间。
3. 将表、来源、时间和记录 ID 游标与删除数量在同一批事务提交到任务结果。
   重启或自动重试从已提交断点继续，避免重复遍历已删除的索引前缀。
   兼容旧任务无结果/无游标的情况。
4. 增加旧节点与大量较新其他节点数据的执行计划及删除回归；中断测试验证持久化游标。
5. 真实任务进一步发现统计刷新写锁争用会耗尽三次任务重试。清理批次遇到写槽/锁等待超时，
   在保留游标的前提下退让重试；非关键进度事件写入失败仅记录警告。仅真实 SQL 超时缩小批量，避免把等待写锁的时间算作批次成本。手动关联重试在同一修订号且节点仍为删除失败状态时继承断点。
6. 写锁获取 deadline 放在完成 BEGIN/ROLLBACK 之后检查，避免外层取消正在执行的事务边界。
   线上原日志存在 `already a transaction in progress`，SQLx 0.8 的 BEGIN 深度是在响应返回后才记录；
   取消中间步骤可能让服务端事务状态与连接池记录不一致。
7. 重试入口直接识别同修订号的失败删除并继续后台路径，不再扫描已经清空的前序历史表。
   首次历史阈值检查抑制顺序扫描并使用定制计划。真实日志证明原阈值检查耗时约 14.87 秒，
   客户端 15 秒退出导致此次请求未入队；新增“清理完成、元数据删除前失败”的重试回归。
8. 在线样本清理后的统计重建也按最多 256 个周期提交，并让出写锁；在线原始样本初始每批 128 条，并保留真实超时缩批。
   保留快照兜底路径的完整一致性，刷新函数返回原始 SQLx 错误以保留诊断与重试类别。
   清理等待统计写锁繁忙时继续退让，避免把暂时繁忙转换成不可重试的通用错误。
9. 周期统计改为删除确实消失的范围、只更新数值有变化的行，避免重写其他节点的相同统计，
   从而不反复触发其他节点分钟汇总重建。关闭短事务统计刷新的 JIT；移除把等待其他写锁的
   时间算入工作批次并过度缩批的启发式，仍保留真实 SQL 超时后的缩批。
10. 本地构建 Linux amd64 镜像并传至服务器。部署后通过现有 API 重试用户已经请求的失败删除，
   观察真实任务直到完成，并验证健康检查、其他节点和错误日志。

## 建索引期间的恢复事件

在线样本索引第一次构建期间，数据库记录 `untracked child process ... exited with exit code 2`，
随后主动终止所有后端并进入恢复。内核日志显示内存压力，但没有本次 OOM 杀进程证据。
数据库恢复后，检查并移除无效的未完成索引，再以 16 MB 维护内存、禁用并行维护的会话重建成功。

现有数据库容器以 PostgreSQL 为 PID 1、健康检查通过 shell 启动 `pg_isready`。
健康检查超时后遗留子进程被 PID 1 收养，是这条退出日志的可能来源；目前没有保留到该 PID 的
直接进程证据，不把它表述为已确证的唯一原因。配置补充 `init: true`、探针 `exec` 和 1 分钟
正常停机窗口，正常停止并重建容器后确认生效，数据库数据卷保持使用原卷。

依据：[PostgreSQL 子进程异常处理源码](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/postmaster/postmaster.c)
与 [Compose init 进程回收说明](https://docs.docker.com/reference/compose-file/services/#init)。

首次真实验收任务 `51e6a119-3170-46e9-9579-be4ccba29ed7` 清理 84,447 条后因写锁/连接等待
耗尽三次重试而失败；98 次公网就绪检查均为 200。该结果促成上述第 5、6 项修复，
不能将索引部署本身表述为完整验收成功。

中间构建镜像 `hysteriax-server:node-cleanup-resume-20261021`，本地二进制 SHA-256
`9b9db44dca97c644b154ff5f3b3f421113de9d7b98f29a7382c00444fee1348a`。
中间镜像 `hysteriax-server:node-cleanup-final-20261021` 本地构建完成，二进制 SHA-256
`f21ee28e29cca7b7d80e02276f169c75eb6b29882fe0abc4764cb9e759a29003`。
`901ad591-ff48-4562-bff3-c6f9f9b6b4de` 沿断点继续至 190,459 条，网络及探测表清空；
在线样本后的统计重建出现长事务，最终将繁忙错误转换为通用协议错误而失败。

这样一次在线批次及少量并发采样通常能在一次统计事务内消化。保留 SQL 超时缩批及事务间退让。

## 最后外键扫描与真实完成结果

原始历史已清空后，最终 `DELETE FROM nodes` 仍在外键级联 SQL 超时。
2026-10-21 02:46 UTC，`traffic_records` 的计划仍估计目标节点有 82,201 行，
选择旧 `traffic_records_node_time_idx` 的 Bitmap Heap Scan。实际已经没有记录；
切换普通索引扫描后，冷读 2,344 个共享缓冲页，查出 0 行仍耗时 3.875 秒。
因此仅关闭顺序扫描、缩小删除批次仍不足以保证最终 2 秒的级联语句成功。

对四张原始历史表执行非 FULL 的 `VACUUM (ANALYZE)`，会话维护内存 16 MB、
禁用并行维护、锁等待 1 秒；不取得应用全局写锁，不修改其他节点业务记录。
原有后台任务在 2026-10-21 02:48:03 UTC 正常提交：

- 任务 `aca29ac6-0821-430c-8925-bc6e7e60f67d` 为 `succeeded / record_removed`，
  最终断点链累计清理 328,430 行，错误为空。
- 目标香港家宽节点消失；八张历史表中该节点记录合计为 0。
- 原有六个节点的 ID 集合仅少目标节点，其他五个节点全部保留。
- 此次继续处理期间 219 次公网 `/readyz` 检查全部为 200，管理节点接口 200，约 280 毫秒。
- 本次为用户已经发起的记录删除，结果记录 `remote_uninstall=false`；没有执行远端卸载。

防复发代码在最终元数据事务之前，使用独立读事务访问相同节点的外键索引路径。
该准备阶段不取得应用全局写锁，每张表单独提交，读 SQL 最长 30 秒；强制普通索引扫描，
让旧索引中的无效条目访问、标记及冷读在写锁外完成。最终级联事务使用相同设置并关闭 JIT，
仍保持 SQL 2 秒限制。线上手工 VACUUM 仅用于本次积压恢复，不由应用每次删除自动执行。

新增回归保留清理前统计和删除后索引条目，用表锁阻塞准备阶段，验证其他应用写事务仍能
取得全局写锁；随后完成最终删除并确认其他节点的 4,000 条流量记录保留。
防复发版本节点删除回归 10 项通过、生产副本显式测试 1 项按设计跳过；
`cargo fmt --all -- --check`、`git diff --check` 通过。

`89f24fd023305d0f9cb7dcce079cd069ff963c4f1fd854fae6e9fd3850bc0794`。
镜像已由本地传至服务器并部署，线上二进制 SHA-256 与本地一致，API 容器健康。
