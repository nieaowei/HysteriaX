# 0012 — 主页面上下分区缩放性能排查

日期：2026-10-07（Asia/Shanghai）
状态：已实施
基线：773d20f

## 范围与定位

用户确认节点、用户、任务、凭据、DNS 等页面在选中记录、展开下方详情后缩放卡顿。

对照先检查共用 `MainVerticalSplitView`：移除 GeometryReader 和随窗口尺寸变化的 idealHeight，可保持默认等分，但单独测试未取得明显性能改善。简单双面板同进程复测中，动态几何方案平均布局 16.1 ms，纯弹性方案 16.3 ms，因此未将其认定为主要瓶颈。

主要开销是详情中 ViewThatFits 的重复候选树：标题与操作、节点连接与套餐、用户额度与节点分配，各自包含横排和竖排两套相同内容，在原生分区的尺寸测量路径中反复布局。改为单一内容树后，展开详情的布局耗时明显下降。

## 实施

1. 共用 VSplitView 改用两组同等弹性尺寸约束，移除持续动态 idealHeight 计算，保留稳定面板身份、180 点最小高度和初始 1:1。
2. 增加 DetailHeaderLayout，以一套标题与操作内容进行横排或竖排，并复用本次测量结果进行放置；节点、用户、任务和凭据详情使用它。
3. 节点连接/任务与套餐、用户额度/节点分配改用现有 OverviewColumnsLayout 单树布局：内容区宽度达到 576 点时等宽双列，否则单列。保留任务位于套餐上方且等宽。
4. 增加独立缩放基准和标题布局检查，扩展分隔条检查，覆盖窗口宽高变化后用户位置保持。

## 对照结果

相同静态夹具、关闭网络、Swift 6、-O 与 whole-module-optimization；每个场景预热后记录 48 帧，宽度 720–1138 点、高度 700–898 点。原版使用 Git 基线源文件单独编译，最终版本复测，测试期间未执行真实节点操作。

| 场景 | 修改前平均布局 ms | 修改后平均布局 ms | 降幅 |
| --- | ---: | ---: | ---: |
| 节点详情 | 53.6 | 15.1 | 72% |
| 用户详情 | 38.1 | 11.7 | 69% |
| 任务详情 | 16.2 | 9.3 | 42% |
| DNS 详情 | 21.3 | 17.0 | 20% |

原始数据保存于 `0012_split_resize_before.json` 和 `0012_split_resize_after.json`。凭据详情复用了相同标题布局并通过构建，本轮页面性能基准不包含凭据详情。

节点仅列表控制组约 209 → 206 ms，未发生实质变化；它不是本次用户确认的展开详情场景。测试中的离屏 bitmap 渲染另有较高开销，上表只报告布局测量，不能换算为实际拖动窗口的 FPS。
