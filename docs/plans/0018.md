# 授权组成员增删延迟优化

日期：2026-10-29（Asia/Shanghai）
状态：已无备份部署并验证

## 问题和证据

用户反馈成员增删仍慢。授权路径中的证书准备和提交按用户 × CA × 版本逐项执行，即使可复用证书也重复往返数据库。移除成员又按节点逐一入队。

隔离的真实 HTTP 对照采用 6 名成员、3 个托管节点、同一 CA、数据库代理双向各增加 12.5 毫秒延迟；连接池 32、采样间隔 60 秒。修改前首次添加 7.174 秒、移除 2.984 秒、重新加入 9.098 秒。调查日志发现重新加入反复在任务锁和事务提交阶段重试。最终定位到两类无关工作：空撤权任务状态清理，以及任务进度和授权变更重复更新同一节点实体缓存计数。

## 最终实现

1. 授权证书准备采用单个只读快照，按 256 项分批读取用户、CA、身份和证书状态；CA 加密材料按版本统一加载并按需解密。签名和加密仍在写事务外完成。
2. 授权证书提交按 256 个身份验证和写入；保留用户修订、身份/授权修订、CA 策略与状态、资格及有效期检查。多 CA 版本分轮处理后续版本，所有批次处于同一事务，任何失败全部回滚。
3. 移除成员按准确用户—节点对批量入队，保持每节点一个共享任务、原因合并、执行代次和事件语义。避免重复写入未变化的执行代次。
4. 重新加入时，撤权原因和代次与权限原子提交。已经没有活跃义务的排队任务交给既有调度器按每批最多 100 个节点清理；忙任务跳过，重新检查义务并记录取消事件，重启后可继续。保存不再读取或修改这些派生任务的状态。任务如已被领取，则执行器按义务和代次继续检查，空任务可直接结束。
5. 新增 `0004_separate_job_cache_roots.sql`：任务更新保留 jobs 域、任务实体与其他根的缓存失效；节点接口本来就依赖 jobs 域，故去掉 jobs 对节点实体计数的重复更新。避免无关任务进度让授权 SERIALIZABLE 提交反复失败。现有版本计数、业务表和权限数据不重置，协议仍为 2，维护后 schema 为 4。
6. 清理旧的逐身份版本准备/提交包装；原单身份签发实现保持不变。更新一个旧 HTTP 验证用例，按现有异步 token 使用记录语义等待并重新触发读取，保留认证、自令牌保护和秘密不泄露断言。

## 验证

- 260 成员、双 CA 版本、跨批次注入失败后整体回滚、重新加入复用原证书通过；260 人的两个版本只需 4 次证书版本批量插入。
- 任务共享、准确用户节点对、其他原因保留和运行中代次回归通过；新增忙任务期间撤权义务可提交、调度器稍后及重启后清理测试通过。
- 缓存回归验证原函数升级保留用户/节点/任务，进度仍使节点响应缓存失效，并发授权能提交；后端 HTTP 缓存回归通过。
- 广泛证书回归采用 8 MiB 测试线程栈（既有双部署大用例在默认测试线程栈溢出，原单身份实现已保持不变）。269 项中 268 项通过，旧同步使用记录断言已按异步语义修正并独立通过。82 项托管证书回归并发运行 81 项通过，一项轮换推进断言独立重跑通过；保留原失败日志，不将其隐藏为一次全绿；最后追加完整轮换串行回归，17 项全部通过。
- 迁移验收通过：维护初始化、原生 schema、两个独立协议 2 实例正常。原 1～3 SQL 保持不变；测试环境独立迁移工具为 `--migrate-only`。
- 最终隔离 HTTP 对照：首次添加 3.538 秒、移除 2.972 秒、重新加入 3.427 秒。小场景移除耗时基本不变；批量入队减少随节点数量增加的 SQL 往返。以上为本地代理测试，不是生产成员操作实测，也不代表 10 万用户与 1 万节点的全量笛卡尔积耗时。
- 私密证据与复测工具保存在 `production/diagnostics/20261029-authorization-member-latency/`。
