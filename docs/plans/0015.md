# 授权保存反馈延迟排查与优化

日期：2026-10-29（Asia/Shanghai）
状态：已实施并通过验证；服务端已无备份部署，详见 0016；客户端未替换运行版本

## 用户问题

创建、修改、删除授权组和用户所属组调整，点击保存后要等数十秒才响应。以 10 万用户、1 万节点为前提排查。

## 排查证据

1. 四个客户端授权写方法在收到服务端成功回执后，仍同步等待 `ManagementStore.refresh()`，之后才向编辑窗口返回结果。这一强制刷新包含版本、凭据、节点、用户、任务、审计、监控、授权组、概览、DNS 等读取。事件推送也会请求同一共享刷新，设置 `pendingForcedRefresh` 后还会追加刷新轮次。
2. 生产本机逐个测量 14 个读取接口：单次约 0.27～3.30 秒。两轮串行探测总计分别 17.738 秒和 13.499 秒；这些是接口基线，不是应用完整刷新实测（客户端部分请求并行）。等待这条读取链以及追加轮次会推迟保存成功反馈。
3. 在生产创建无成员、无节点的临时空组，再修改名称并删除，三个提交分别为 5.210、6.132、3.367 秒，均新增/移除 0 条授权，临时组已删除。说明服务端提交本身也非瞬时，不能把全部延迟归因于客户端。
4. 生产到数据库的八次 `SELECT 1` 往返约为 25～138 毫秒。服务端授权路径中存在按成员、节点、连接和托管身份逐条 SQL 的循环；这些往返会随变更规模增长，并延长资源持锁时间。
5. 生产日志存在节点/租约相关的秒级慢查询；单次活动快照中有短时事务等待，未见连接池超时。没有据此断言数据库完全没有锁竞争。
6. 只读探测、慢日志摘要和临时空组测量保存在本地私密目录 `production/diagnostics/20261029-authorization-save-latency/`；未改动现有授权或生产配置。

## 修复

1. 四种客户端授权操作收到成功回执后立即返回，后台继续使用已有共享刷新机制。创建、修改、删除的授权组信息直接用服务端回执更新列表，并使旧组读取失效，避免旧响应覆盖新结果。
2. 刷新仍会使列表缓存失效，但保存成功结果不再依赖监控、DNS、概览等读取。结果页的完成按钮不再受成员/节点目录加载状态禁用；仍以服务端写成功作为显示成功的依据。成员/节点编辑按需加载相应目录，改名和用户所属组调整不再加载无关的全量用户/节点目录，成功结果页也不再触发选择目录读取。
3. 服务端成员关系、节点关系、用户修订、用户所属组关系和组修订改用集合 SQL；连接密码仍在事务外逐对独立生成，事务内批量写入，每对的哈希、密文和一次性回执保持对应。
4. 重新授权时只批量清除准确的用户—节点对上的 `authorization_group_removed` 原因，保持其他原因、交叉连接、执行代次和节点共享撤权任务；只有队列中无活跃需求的任务才取消，取消事件批量记录。
5. 托管身份及凭据归档改为批量更新，结果中的受影响节点一次查询后按用户/CA 对分组。用户所属组响应中的授权来源一次 SQL 返回，消除每节点一次查询。
6. 保留事务、修订冲突、幂等回放、证书校验、撤权代次和审计语义；无数据库结构或协议变化，不需要数据迁移。

## 验证

1. 客户端回归通过：人为阻塞刷新读取，分别验证创建、修改、删除授权组和修改用户所属组均能在读取释放前返回成功结果。
2. macOS 界面测试通过：全局监控读取延迟 8 秒时，保存结果在 4 秒内出现；随后用户目录读取延迟 8 秒时，“完成”按钮仍可用。结果记录：`apps/macos/.build/authorization-ui-1793215745.xcresult`。
3. macOS 正常应用 Debug 构建通过；未启动或替换用户正在运行的应用。
4. 服务端授权回归 27 项、撤权回归 11 项、托管证书回归 81 项、激活所有权回归 12 项通过，真实 HTTP 授权验收通过。另有 17 项轮换专项通过（包含在上述托管证书回归中，不重复计数）。
5. 新增千人成员授权回归通过：成员插入、授权插入和用户版本更新各为一次集合写入；1000 个密码独立且摘要、密文与用户对应。新增精确用户—节点对撤权回归通过，交叉连接、其他撤权原因和共享任务得到保留。
6. Rust 格式、API 模型生成检查、1948 条双语资源检查和差异空白检查通过。临时本地测试数据库已移除。

排查结束时尚未部署。后续服务端部署和生产验证见 0016；客户端修复未替换运行版本。原有生产空组提交仍有约 3.4～6.1 秒基线，解除客户端额外等待不等于服务端提交瞬时完成。
