# Compatibility profile

## macOS client architectures

The client is built as a Universal app with `arm64` and `x86_64` slices. Its deployment floor is macOS 26.0 so the Intel slice remains usable on Intel Macs, for which macOS 26 is the last supported major release; macOS 27 runs on Apple silicon only. The app runs on macOS 27 and later on the native `arm64` slice. A single deployment target of macOS 27 would make the Intel slice unusable, so the plan uses macOS 26 for the Universal artifact and macOS 27 as the Apple silicon acceptance baseline. See [Apple's macOS 27 compatibility guidance](https://support.apple.com/en-us/127455) and [Xcode 27 architecture notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes?changes=l_2_3&language=objc).

The server downloads only Hysteria 2 `app/v2.12.3` and verifies the Linux amd64/arm64 binary digests recorded in [deploy/hysteria-v2.12.3.sha256](../deploy/hysteria-v2.12.3.sha256). Node traffic is not directed to a moving upstream version.

The Mihomo subscription shape is pinned to v1.19.31. `scripts/verify-subscription.sh` creates a subscription through the Rust API, checks current-token retrieval and old-token revocation after rotation, marks its fixture node as deployed, and validates the emitted file with Mihomo's own config validator. It also verifies that a user with no node assignments gets a DIRECT-only empty configuration that parses with Mihomo. `scripts/verify-mihomo-config.sh` downloads only the selected v1.19.31 asset and checks its SHA-256 before running `mihomo -t`.

The automated subscription fixture uploads an ECH key resource and checks its generated `ech-opts`, Gecko settings, and port range with pinned Mihomo v1.19.31. It also covers mTLS client certificate fields. A disposable Debian 13 arm64 node passed real TCP and SOCKS5 UDP forwarding through the pinned Hysteria client.

ECH is supported with an uploaded encrypted ech_key resource. HysteriaX deploys the private key to the node and extracts the public ECH config list into the no-store subscription. Port hopping accepts single-port lists and ranges, prechecks for nftables/iptables, and grants CAP_NET_ADMIN only to that node's systemd service. A disposable Debian 13 arm64 run completed 2 MiB TCP transfers through both the pinned Hysteria client and Mihomo v1.19.31 with ECH, Gecko, mTLS, and 5-second hopping enabled.

Before a deploy or sync that enables mTLS, assign at least one user with a matching client certificate and private key. The deployment worker uses that certificate with a short-lived internal probe credential, then forwards a TCP request through the pinned Hysteria client to the node's local stats API or configured `proxy_probe_url`. Each node can set an optional `proxy_probe_url` when custom ACL or outbound rules block the loopback destination; the URL must be an HTTP 200 endpoint reachable through the configured route and must not contain credentials or query parameters. Without a custom target, the worker reports authenticated-session verification when policy blocks loopback traffic.

Realm mode is supported with Hysteria v2.12.3 and Mihomo v1.19.31. Mihomo's default five-second caller context can expire during Realm discovery, rendezvous, and QUIC authentication; the upstream report identifies STUN discovery as taking up to 6.5 seconds ([issue 2863](https://github.com/MetaCubeX/mihomo/issues/2863)). Mihomo added a `handshake-timeout` option in [v1.19.30](https://github.com/MetaCubeX/mihomo/releases/tag/v1.19.30); HysteriaX emits `handshake-timeout: 30` for Realm subscriptions so setup can continue under a client-owned deadline. The server renderer places the configured listener port in the Realm URI as `lport`, and deployment probes use the Realm URI plus the client tuning fields. `scripts/verify-realm-live.py` runs the pinned Mihomo v1.19.31 against a self-hosted rendezvous with a 5.6-second STUN response: the transfer fails without `handshake-timeout` and forwards 2 MiB with it. A proposed upstream context fix ([sing-quic PR 5](https://github.com/MetaCubeX/sing-quic/pull/5)) remains unmerged; the pinned-client workaround is covered by the live regression script. Realm cannot be combined with port hopping. Enabled Mimic remains disabled because there is no Mihomo mapping. A four-distro arm64 systemd-container matrix also verified deployed two-node/three-user auth isolation and aggregate quota enforcement. Independent Debian 12/13 x86_64 cloud VMs passed deployment, three-user assignment isolation, live revocation/rotation, and usage sampling. Server2 also passed mTLS deployment and live TCP HTTPS transfers through both the pinned Hysteria v2.12.3 client and Mihomo v1.19.31 using its generated subscription; the original node configuration was restored afterward. The cloud SSH interruption/retry path also recovered successfully. A managed-listener UDP conflict on Server2 also triggered automatic rollback and explicit recovery. The occupied-port preflight guard was also exercised on Server2 with a temporary marker backup/removal and explicit recovery; Server1 clean first-install and unmanaged-directory refusal passed with snapshot, restore timer, service restoration, and API-readiness checks; Server1 clean install and initial-install UDP-occupancy rejection/retry also passed with service restoration verified. Forced rollback failure and explicit recovery pass on Server2. Native amd64 and arm64 runner matrices passed for all four supported distributions ([run](https://github.com/nieaowei/HysteriaX/actions/runs/36804870498)).
