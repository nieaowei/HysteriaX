# 后端缓存与预聚合梳理

日期：2026-10-13。依据当前工作区代码，包括尚未提交、尚未部署的 0025 概览聚合改造。本次为代码审查与方案梳理，未修改运行逻辑、未访问生产数据库做性能测试，也未实施下表建议。优先级依据重复计算、数据增长方式和调用链，实际收益需结合请求频率、SQL 耗时和缓存命中率确认。

## 1. 结论与分类

后端的主要机会分为四类：

- **短期响应缓存**：概览、历史趋势、重复查询的目录摘要。
- **按版本缓存计算结果**：节点脱敏配置预览、订阅格式生成、不可变资源解析和固定版本安装包。
- **持久化派生数据**：历史趋势桶、用户/节点累计流量、凭据引用关系。前两种是统计聚合；引用关系是需要强一致维护的索引。
- **先优化读取方式**：管理员鉴权、节点/用户/授权组的逐条关联查询、SSE 独立轮询、任意关键词搜索。不能简单用缓存代替这些改造。

现有 `users.usage_bytes`、`node_packages.usage_bytes` 已在采样事务内增量维护，属于实时计费状态；不需要再从历史记录预聚合重建后用于鉴权。主机资源采样也已经有 2 秒缓存。

| P2 | 资源与配置解析；采样/探测 worker | 重复解析固定版本凭据/资源、配置及证书，重新构建 HTTP 客户端 | 优先缓存无秘密的解析/校验结果及配置投影；复用 HTTP 客户端属于连接优化 | 配置快照按 revision；采样结果仍实时写入 | 不缓存 SSH 信任判断、租约或执行状态；首批不增加通用明文凭据缓存 |

TTL 均为初始候选，不是已经采用的接口新鲜度承诺。静态数据、可变状态与授权判断应分别处理。

## 3. 最值得做的持久化派生数据

### 3.1 历史趋势

数据源为 `traffic_records`、`node_network_samples`、`online_samples`、`proxy_probe_samples`。

建议设计三个读模型：

1. **流量时间桶**：节点、必要时用户/计费周期、UTC 桶起点、发送/接收总量、有效样本数、基线/缺口标记。累计原始 `delta_tx/delta_rx`，不从累计计数器直接相加。
2. **在线采样周期统计**：保存每个 `cycle_id` 的全局跨节点去重用户数、连接总数、覆盖/预期节点数、有效/不完整状态；另保留单节点维度以支持节点筛选。
3. **探测桶统计**：尝试数、成功数及延迟统计需要的原始分布或可合并数据。

不能相加各节点的在线人数来得到全局人数，也不能平均各小时平均值或 P50/P95。在线桶平均应从有效周期值的总和与有效周期数计算，保持现有“每采样周期平均”的含义。精确 P50/P95 先继续读取原始延迟；使用分布摘要会引入近似误差，需要另行定义精度。

**滚动窗口是实现前必须处理的边界**：现有 `date_bin` 以请求时刻减去 24h/7d/30d 为起点，并非 UTC 整点自然日。简单建立整点小时表不能精确替代它。

- 可以选择较细的基础桶，例如 1 分钟；每个展示桶读取完整基础桶，边缘部分读取原始记录。
- 边缘不仅是整个查询窗口的头尾，每一个未对齐的展示桶都有边界。
- 若将缓存查询终点固定到整分钟以便直接组合基础桶，必须在响应中明确 `as_of/generated_at`，接受并记录其新鲜度；不能悄悄改成自然日统计。

聚合按源记录幂等处理或重算完整目标桶，允许迟到样本回补。采样周期应在结束/超时规则下计算覆盖状态，不能提前把尚未采集的节点当成失败或零值。缓存键包含聚合算法版本、水位/查询终点与维度。

当前清理器删除超过 30 天的 `online_samples` 和 `proxy_probe_samples`。接入聚合后，应确保清理发生在必要聚合完成之后，并为迟到回补、缓存窗口及原始边界查询保留余量。不要提前删除仍用于精确百分位数的样本。

### 3.2 用户按节点累计流量

`users::usage` 对该用户全部历史记录执行 SUM，并查询历史参与节点。访问频繁、历史不断增长时，适合新增按 `(user_id,node_id)` 维护的累计读模型：

- 发送/接收累计值、最后采样时间，以及回补/校验水位。
- 当前是否分配该节点、节点显示名称和用户是否受限，在读取时查询当前业务状态。
- 与采样写入事务同步增量更新，或者用源记录 ID 幂等消费；历史回填与新增记录交接必须避免重复累计。
- 需要重算和对账入口，避免永久依赖不可校验的累加结果。

当前接口的按节点历史累计没有按 `quota_reset_at` 过滤；它与可重置的 `users.usage_bytes` 不是同一统计口径。若另外增加按账期累计，必须增加账期维度并明确字段含义。预聚合仅服务展示，不替代当前计费、超额和撤权判断。

### 3.3 凭据引用关系

这比“缓存整个凭据详情”更有长期收益：现有 `find_references_on` 每次遍历目标配置、部署配置及所有历史版本，解密后提取引用。

建议建立引用边表，保存凭据 ID/版本、对象 ID、来源（SSH/目标/部署/历史/分配/DNS/活动批次）、配置修订号及字段路径。只保存引用关系，不复制秘密载荷。

**必须保留两种不同口径**：

- 目录 `reference_count`：按当前使用对象去重；同一节点的目标、部署及 SSH 引用合并为一个节点对象。
- 详细引用与删除检查：还包括历史版本、具体字段路径及活动批次，不能套用目录的去重计数来决定能否删除。

引用索引若用于删除、归档、发布校验，应在相应业务事务内同步维护，覆盖配置保存、部署确认/回滚、历史版本写入、节点/分配删除、DNS 连接和批次变化。回填完成并验证前继续使用原校验逻辑；不能让异步刷新中的旧索引放行破坏性操作。

## 4. 缓存键、失效和读取边界

| 数据 | 键的主要组成 | 失效来源 |
|---|---|---|
| 概览 | 实例/权限范围、响应版本、相关数据 generation | 采样、任务状态、用户/节点/套餐变更；时间条件用短 TTL 或到期点限制 |
| 历史趋势 | 节点、范围、来源、指标集合、时区、查询终点、算法版本/水位 | 新样本、迟到回补、清理及聚合版本变化 |
| 凭据目录 | 目录/引用 generation、分类、类型、搜索、排序、页码/条数 | 凭据/节点/用户/分配/DNS/订阅/管理员 Token 变化；到期状态重新判断 |
| 节点预览 | 节点 ID、目标/部署修订号、依赖凭据版本、资源内容摘要、模板版本 | 配置、依赖或模板变化；实时套餐/采样不放入该静态缓存 |
| 用户/组展示 | 对象及成员关系 generation、筛选/分页参数 | 用户/节点/授权组成员和绑定变更 |
| 订阅生成部分 | 用户、当前可用节点集、部署/分配/凭据版本、输出格式、客户端能力 | 用户/节点资格及部署/凭据/分配变化；资格检查每次执行 |
| 任务/发布批次 | 对象 ID、更新时间/状态 generation、重试关联及相关名称版本 | 任务进展、日志、重试、批次变化、节点改名 |
| 安装包/不可变解析 | 发布版本、架构、内容摘要或明确的资源版本 | 内容/版本变化、容量淘汰；安装包重新使用时验证摘要 |

公共实现应包含：有界内存/条目容量、相同键请求合并、TTL/时间到期点、事务提交后失效、 generation 检查、命中/等待/失败指标及必要的手动绕过缓存。不要无限保存任意搜索字符串和 User-Agent 组合。

缓存填充期间如果 generation 改变，旧结果不能发布到新版本缓存。写入提交后、成功响应前完成相关失效，保证用户写后刷新不会读到旧页面。总数与 items 应来自同一个缓存快照或数据库快照，不能分别缓存为不同版本。

当前进程有数据库单实例锁，适合先使用进程内缓存。业务写入和 worker 都需要触发失效；现有 SSE 主要来自 `job_events`，不能假设所有配置、授权、用户用量变化都已经提供完整的失效事件。可先用提交后明确失效钩子，持久派生数据再考虑事务内维护或 outbox。

缓存只在鉴权之后读取。管理缓存也要区分响应里的身份相关信息。订阅响应包含用户凭据，应保持用户隔离，不进入公开共享 HTTP 缓存；首批优先复用无秘密的计算部分。

## 5. 应先批量化或共享读取的地方

- `node_json` 同时用于节点分页和详情，逐节点读取套餐、任务、绑定、资源并渲染配置。先将分页关联数据批量读取，并使列表不承担详情专用的预览计算，再缓存静态结果。
- `user_json_on` 存在“用户 → 分配 → 权限来源”的嵌套查询。可以一次读取当前页用户的分配和组关系，再按 ID 装配。
- 授权组列表逐组开启事务并读取完整成员名单。成员数量和成员明细应分别按需求读取。
- 凭据详情循环读取多个发布批次；批次内部已经使用 JOIN 读取任务项，优化重点是多个批次的批量加载及按需返回历史批次。
- DNS 展示本来从本地数据库读取，不应为缓存展示引入额外提供商请求。提供商 HTTP 客户端连接复用和刷新请求合并可另外优化。
- SSE 采用一个或少量共享读取器读取提交后的持久事件，再分发给连接；缓冲外的游标仍从数据库补读，不能用缓存替代持久回放。
- 任意关键词搜索的 COUNT 和深页 OFFSET 先看执行计划与索引。无筛选总数或按状态计数的派生结果，不能回答任意字符串筛选的精确匹配数。

客户端目前每 15 秒全局刷新，并且 SSE 收到事件后可能再次触发全局刷新。这会放大目录装配与鉴权写入成本。虽然本文件聚焦后端，实施前应同时测量这些触发频率，避免缓存 TTL 小于请求间隔而几乎没有命中。

## 6. 不进入普通缓存的决策与操作

- `/hy2/auth` 的允许结果、Token 撤销、用户停用/到期/超额、节点套餐限制及权限归属判断。
- 授权组写入预览确认、修订号冲突检查、凭据删除/发布校验及绑定验证。
- 任务领取、租约、撤权执行、部署/回滚/删除、DNS 写入前冲突判断与写后确认。
- 采样基线、计费用量、账期重置、计数器回退/重启处理和幂等标记。
- `/readyz` 的数据库就绪判断；错误或鉴权失败默认不进入业务响应缓存。

这些流程可以复用不可变解析结果或采用更少的 SQL，但数据库事务、当前资格判断及外部执行确认仍是操作依据。主机监控中已有的 2 秒资源快照复用与业务放行决策不同。

## 7. 建议实施顺序与验收

1. **先测量并减少公共成本**：按 Token 唯一索引读取、明确 `last_used_at` 更新精度；拆开客户端概览/目录刷新；SSE 共享读取。记录各路由请求次数、查询次数、池等待、写锁等待和响应大小。
2. **缓存明确可复用的结果**：历史趋势同键合并和短 TTL、概览短 TTL、固定摘要/版本计算、固定版本安装包。观察命中率及缓存失效后的并发查询数。
3. **减少逐条读取与目录重建**：节点/用户/授权组关联数据批量化；凭据目录同版本快照共享；引用索引完成回填与一致性验证。
4. **再引入持久统计读模型**：用户/节点累计流量；历史周期统计及基础时间桶。验证 24h/7d/30d、节点过滤、迟到、清理、缺口、账期重置、用户去重与百分位数。

验收至少涵盖写后读取、撤销立即生效、缓存填充与写入并发、相同键单次计算、容量限制、跨用户隔离、数据库/外部提供商失败、聚合重跑幂等及原始数据对账。计费与执行流程的正确性不能用缓存命中率替代。
