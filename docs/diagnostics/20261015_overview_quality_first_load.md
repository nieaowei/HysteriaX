# 概览连接与质量趋势首次加载诊断

日期：2026-10-15（Asia/Shanghai）。代码基线：00fff95；线上镜像：cache-rollups-20261014-v2。

## 已确认

1. 客户端进入质量趋势时立即请求 metrics=quality；没有等候 60 秒再首次请求的逻辑。60 秒是后续刷新间隔。客户端缓存可显示已有趋势，首次没有缓存时需要等整个响应。
2. 服务端依次取得一致性快照、在线连接汇总、探测成功率和延迟分位数，全部完成后一次返回。响应缓存未命中时，上述耗时累加。
3. 服务器本机 HTTPS 强制绕过响应缓存，首轮 users/quality 的 24h、7d、30d 分别为 677.87、1531.07、714.46 ms；后续两轮约 60.77–187.93 ms。quality 不受 source 影响业务内容，network 第二组同样查询已较快。
4. 单节点首轮 24h、7d、30d 测得 3717.62、1387.01、74.94 ms，同节点第二次 24h 为 45.67 ms。另一个节点的 7d 请求 2055.79 ms，期间一个 PostgreSQL 进程新增 131 次主要缺页；30d 请求 817.04 ms，另一个进程新增 85 次主要缺页；随后 24h 为 59.9 ms，无新增主要缺页。主要缺页意味着需要磁盘调入页面，这是秒级冷请求期间真实出现的读盘证据。
5. API 日志记录在线汇总查询耗时 1.63–2.38 秒，以及探测查询约 2.03 秒。秒级慢请求确实出现在服务器 SQL 路径内，并非仅客户端渲染等待。
6. 在线查询的 edges 分支普通 JOIN 被规划成先扫描 online_cycle_metrics，再与补算范围连接。对齐分钟的 24h 窗口、补算范围为空时，仍扫描该表，输出范围下的 47,630 行后最终边界返回 0 行。分钟汇总实际返回约 1,434 行。
7. 只读 EXPLAIN ANALYZE 对比：原在线 SQL 执行 36.289–61.951 ms；把 edges 改成由 ranges 驱动的参数化 LATERAL 查询（OFFSET 0 阻止展开）后 3.8–5.165 ms。改写后 online_cycle_metrics 索引分支 Actual Loops=0，没有补算范围时完全跳过。此为只读候选查询验证，尚未修改生产查询。
8. 原查询首次规划测得 75.589 ms，同连接再次规划 1.83 ms；另一个新连接规划 2.838 ms。首次规划和数据库缓存状态会带来额外开销，但这些数字不足以解释全部秒级波动。
9. 探测次数和成功率已从分钟汇总读取；精确 P50/P95 仍读原始成功探测样本并排序。24h 实测读取约 7,133 条延迟样本，探测查询执行 14.428–18.493 ms。预聚合不覆盖精确分位数排序。

## 环境与证据限制

测试服务器可用内存约 964.6 MiB，vmstat 显示约 499 MiB swap 已使用。采样时 CPU 空闲约 88–93%，API 内存约 33 MiB、数据库容器约 273 MiB。数据库后台进程在秒级请求期间产生了主要缺页增量，已变快的 HTTP 请求则没有。结合交换空间占用，内存压力和冷页面调入是重要影响因素；主要缺页计数本身不能区分匿名页面换入和文件映射缺页，因此不把全部延迟归因于 swap 或认定内存是唯一原因。

本地访问 readyz 的一次新连接测得 TLS 完成 444.553 ms、总耗时 674.071 ms。它证明客户端网络建连可额外增加首访耗时，但不能解释服务器本机 SQL 的秒级慢日志，也不能代表已复用连接时的开销。

历史接口仍可能在存在未处理在线周期时同步处理聚合并等待共享写入锁；本次采集的慢日志主要落在在线和探测 SELECT，尚未获得该等待对首轮耗时的独立计时。

## 优先改进

1. 修正在线趋势边界补算的执行计划，消除空补算范围仍扫描周期表的问题；补齐非对齐窗口、单节点和存在脏分钟时的等价性测试。
2. 增加 history_at 的连接/快照、聚合等待、在线查询、探测查询和响应阶段计时，区分业务 SQL 执行与首次准备开销。此次对比不能把 36–62 ms 的多余扫描直接宣称为秒级延迟的全部原因。
3. 在保持精确分位数口径的前提下评估原始延迟样本读取、索引及首次查询缓存；不应仅靠预热隐藏问题。
4. 若计时与主要缺页增量确认关联，再调整数据库连接池和服务器内存配置。

本次进行了只读接口测量和 EXPLAIN ANALYZE；未重启服务或数据库，未部署代码，未更改数据库配置。
